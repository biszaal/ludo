# 1.3.2 Native Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A 1.3.2 store build with a ratings prompt after wins, Android install-source tracking (which also records referrals from a friend link), and a device check that stops one phone from farming referral coins.

**Architecture:**

- **Server:** migration 0084 adds `install_sources` and `user_devices`, widens `referrals` (a `link` source and a `rejected` status), and teaches `referral_settle` the device rule. The `game` function gets two write-once ops.
- **App:** adds `expo-store-review` and `expo-application` (native, hence the store build), reports the install referrer and a device ID once, and asks for a rating at the right moment.
- **Website:** passes a friend code from the landing link into the Play Store referrer.

**Tech Stack:** Supabase (SQL + Deno edge), Expo SDK 58 / React Native, the website (CRA on Vercel), EAS Build and Submit.

**Spec:** the scope Bishal delegated on 21 Nov 2026 (Notion row "1.3.2 native build"). The calls made, recorded here:

- **PR #7 is dropped.** Sign in with Apple runs as a web login through Supabase (`linkIdentity`), not Apple's native dialog. The entitlement it adds is only for the native dialog, and it would force new provisioning (the 1.3.0 build 34 failure).
- **Device ID:** Android uses `Application.getAndroidId()`, which survives a reinstall and is scoped to our signing key. iOS uses a random UUID kept in the keychain. The server stores only `sha256("ludo-device:" + id)`, never the raw ID.
- **Device rule:** a referral is rejected, with nothing paid, if the invitee's device was already used by the inviter, or by an invitee whose referral already paid.
- **Ratings ask:** after a win, from the 3rd finished game, at most once per 90 days, only when `StoreReview.isAvailableAsync()` is true. (Built with `isAvailableAsync`, not `hasAction`: `hasAction` is also true when the fallback would open the store page, which takes the player out of the app.) Skipped when the notification sheet showed for the same win.
- **Install referrer:** read once on Android's first launch. Store its utm fields and an optional `friend` code; a valid friend code records a referral with source `link`.
- **Sentry source maps for over-the-air updates** are a publishing step (`npx sentry-expo-upload-sourcemaps dist` after `eas update`), not part of this build.

## Global Constraints

- Migration **0084**. Money-path changes need SQL tests (PGlite).
- Bots are never part of referrals or devices. No UI text about bots.
- Version 1.3.2. Builds use the Xcode 26 image already pinned in `apps/mobile/eas.json`.
- Order: deploy the server (0084 + `game`) BEFORE the builds reach stores. Done 21 Nov: 0084 applied, `game` v64. Old apps never call the new ops, and the device rule only applies once hashes exist.
- Privacy: website policy lines for the install source and device check. The Play data-safety and App Store label updates stay with Bishal.
- Store submission: Android to production via EAS, iOS uploaded to App Store Connect. The review submission there is Bishal's click.

## Review Focus

1. **An install with no referrer, or a referrer that isn't ours.** Nothing breaks, and `utm_*` is stored only when present. Task 1 and Task 2 tests cover it.
2. **The same device signing in to a second account.** Two `user_devices` rows share one hash; the rule rejects only referrals, never normal play. Task 1 test.
3. **A friend link opened when the app is already installed.** It opens Add Friend with the code looked up, so the existing lookup records the referral. Task 3 test of the URL parser.
4. **The ratings prompt firing on a loss or on every win.** Task 3 tests the gate.
5. **A reinstall on Android.** The Android ID is the same, so the device hash matches and a farmed referral is rejected. Task 1 test.

### Task 1: Migration 0084 and SQL tests

**Files:** create `supabase/migrations/0084_install_and_device.sql`, `scripts/tests/installDevice.test.mjs`.

**Produces:**

- `install_sources(user_id uuid pk → auth.users cascade, platform text, referrer text, utm_source text, utm_medium text, utm_campaign text, friend_code text, created_at)`.
- `user_devices(user_id → auth.users cascade, device_hash text check length 64, created_at, primary key (user_id, device_hash))`.
- RLS on both, no policies.
- `referrals` checks widened: source in (`code`, `room`, `link`); status in (`pending`, `rewarded`, `inviter_capped`, `rejected`).
- `install_source_record(p_user, p_platform, p_referrer, p_utm_source, p_utm_medium, p_utm_campaign, p_friend_code) returns jsonb`. Write-once per user (`on conflict do nothing`); text fields are trimmed to 200 characters. A friend code that resolves via `friend_codes` to another user calls `referral_attach(p_user, owner, 'link')`. Returns `{recorded, referral}`.
- `device_record(p_user, p_hash) returns boolean`. Inserts if new; ignores bots.
- `referral_settle`: after the games and time checks, before paying: if `user_devices` shows the invitee's hash also on the inviter, or on another invitee whose referral status is `rewarded` or `inviter_capped`, set status `rejected` and `qualified_at`, return `{paid:false, rejected:true}`.

Tests:

- install source records once with utm fields;
- a friend code in the referrer attaches a `link` referral;
- an unknown code attaches nothing;
- the device rule rejects for an inviter-shared device and for a second payout on one device;
- a different device pays normally;
- the existing referral tests still pass.

### Task 2: Edge ops

**Files:** create `supabase/functions/game/install.ts` and `install.test.ts`; modify `index.ts`.

**Produces:**

- `parseReferrer(raw: string): { utmSource?, utmMedium?, utmCampaign?, friendCode? }`. Query-string parse; the friend code must match the friend-code alphabet.
- `deviceHash(id: string): Promise<string>`, the SHA-256 hex of `"ludo-device:" + id`.
- `opInstallSource(admin, userId, platform, referrer)` and `opDeviceSeen(admin, userId, deviceId)`. Both rate-limited, both validate (referrer at most 500 characters; device ID 8–128 characters).
- Router: `case "installSource"` and `case "deviceSeen"`.

### Task 3: App

**Files:**

- Create: `src/lib/review.ts`, `src/lib/installSource.ts`, `src/lib/deviceId.ts`, and tests for each.
- Modify: `src/lib/inviteLinks.ts` (the `?friend=CODE` link), `src/lib/invite.ts` (handle a friend link: open Add Friend with the code), `src/screens/AddFriendScreen.tsx` (accept a prefilled code), `src/lib/feedback.ts` (ask for a review on a win), `src/lib/referrals.ts` (share text uses the friend link), `App.tsx` (report the install source and device once at start), `package.json` (`npx expo install expo-store-review expo-application`), `app.json` (version 1.3.2).

**Tests:**

- `shouldAskForReview` gate: a win, at least 3 games, the 90-day gap;
- `friendCodeFromUrl` accepts `https://www.biszaaltech.com/games/ludo?friend=K7PXQ2` and rejects bad codes and hosts;
- `friendInviteUrl(code)`;
- the install-source "once" flag;
- the device "once per account" flag.

### Task 4: Website

Without a friend code, use `utm_source=website&utm_medium=landing`. Privacy policy: install-source and device-check paragraphs, Ludo only. Tests in the site's suite.
